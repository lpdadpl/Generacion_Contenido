Los nombres de herramientas, límites y requisitos de cada servicio cambian con frecuencia. Los ejemplos son orientativos: comprueba la documentación oficial de cada proveedor antes de implementar.

1. Arquitectura en capas

Cada agente solo habla con sus herramientas. Las herramientas se exponen por MCP y los archivos pasan de un agente a otro a través de una carpeta compartida con un manifiesto.

OrchestratorCrea la tarea, la reparte, guarda el estado en la base de datos y reintenta si algo falla.
AgentesCreativo, Generación y Distribución. Cada uno con su propio modelo, sus herramientas y sus claves.
Servidores MCPHiggsfield (vídeo), sistema de archivos, base de datos y redes sociales.
ServiciosHiggsfield, Instagram, TikTok, YouTube, proveedores de modelos de lenguaje y Ollama local.
AlmacénCarpeta del dispositivo (o disco/bucket sincronizado) donde viven los vídeos y sus manifiestos.

2. Cómo funciona MCP

MCP (Model Context Protocol) es un protocolo para que un modelo use herramientas externas con un formato común. El agente actúa de cliente y cada servicio se expone mediante un servidor MCP.

Tools

Acciones que el modelo puede pedir: generar un vídeo, consultar un trabajo, publicar.

Resources

Datos que se leen: el AGENTS.md de la serie, el historial, el manifiesto.

Transporte

Local por entrada/salida estándar (un proceso en tu máquina) o remoto por HTTP con autenticación.

El ciclo es siempre el mismo: el agente lista las herramientas del servidor, el modelo decide cuál llamar con qué argumentos, el cliente la ejecuta y devuelve el resultado al modelo.

Declarar los servidores

{
  "mcpServers": {
    "higgsfield": { "url": "https://mcp.higgsfield.ai/mcp" },
    "archivos": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/media/videos"]
    },
    "redes": {
      "command": "python",
      "args": ["servidores/redes_mcp.py"],
      "env": { "TIKTOK_TOKEN": "${TIKTOK_TOKEN}",
               "IG_TOKEN": "${IG_TOKEN}" }
    }
  }
}

Los servidores remotos suelen autorizarse por OAuth al conectarlos; los locales reciben sus secretos por variables de entorno.

Qué herramientas ve cada agente

No todos los agentes deben ver todos los servidores. El de generación ve Higgsfield y archivos; el de distribución ve archivos y redes; el creativo solo lee fichas e historial. Así un fallo o un prompt malicioso no puede publicar nada desde el agente equivocado.

3. Un modelo distinto para cada agente

Se define en un único archivo de configuración. El código del agente no cambia: solo cambia a qué proveedor y modelo apunta.

# config/modelos.yaml
proveedores:
  ollama:      { base_url: "http://localhost:11434/v1", key_env: null }
  openrouter:  { base_url: "https://openrouter.ai/api/v1", key_env: OPENROUTER_API_KEY }
  openai:      { base_url: "https://api.openai.com/v1",  key_env: OPENAI_API_KEY }

agentes:
  orchestrator: { proveedor: openrouter, modelo: "<MODELO_POTENTE>",  temperatura: 0.2 }
  creativo:     { proveedor: openai,     modelo: "<MODELO_CREATIVO>", temperatura: 0.9 }
  generacion:   { proveedor: ollama,     modelo: "llama3.1:8b",         temperatura: 0.1 }
  distribucion: { proveedor: ollama,     modelo: "llama3.1:8b",         temperatura: 0.1 }

Local o servicio con el mismo código

Ollama, OpenRouter y otros proveedores aceptan el formato de la API de OpenAI, así que basta cambiar la URL base y la clave.

import os, yaml
from openai import OpenAI

CFG = yaml.safe_load(open("config/modelos.yaml"))

def cliente_para(agente):
    a = CFG["agentes"][agente]
    p = CFG["proveedores"][a["proveedor"]]
    clave = os.getenv(p["key_env"]) if p["key_env"] else "ollama"
    return OpenAI(base_url=p["base_url"], api_key=clave), a

OrchestratorPlanificar, decidir, recuperar erroresModelo potente de servicio
CreativoGuiones, ideas, variacionesModelo de servicio con buena escritura

Un modelo local necesita que el modelo elegido soporte llamadas a herramientas. Pruébalo antes de asignarlo a un agente que dependa de ellas.

Una clave por servicio

Si una se filtra, se revoca sin tocar el resto.

Mínimo privilegio

Cada proceso recibe solo las variables que necesita.

Tokens de redes

Usan OAuth: se guardan por cuenta, caducan y hay que renovarlos con el token de refresco.

En producción, mejor un gestor de secretos del servidor o del sistema (por ejemplo, el de tu proveedor cloud) que un archivo en disco. Nunca pongas claves dentro de AGENTS.md ni en los prompts.

5. Generación, solicitud y descarga

La generación de vídeo es asíncrona: se envía el trabajo, se espera y se recoge el resultado.

  1. El Orchestrator crea la tareaRegistra un id en la base de datos con estado pendiente y el JSON del creativo.
  2. Generación lanza el trabajoLlama a la herramienta de vídeo del servidor MCP y guarda el job_id. Estado: generando.
  3. Espera con sondeoConsulta el trabajo cada cierto tiempo, con un límite de espera y de reintentos.
  4. Descarga a la carpeta del dispositivoAl terminar, baja el archivo a /media/videos/inbox/. Estado: descargado.
  5. Verificación y postprocesoComprueba que el archivo abre, mide duración y formato, recorta, añade música o subtítulos y guarda en listo/.
  6. ManifiestoEscribe un JSON junto al vídeo con título, descripción, hashtags, plataformas y hora. Es el relevo hacia el agente de subida.

Descarga y manifiesto

import requests, json, subprocess, pathlib

def descargar(url, destino):
    with requests.get(url, stream=True, timeout=120) as r:
        r.raise_for_status()
        with open(destino, "wb") as f:
            for trozo in r.iter_content(1 << 20):
                f.write(trozo)

def verificar(ruta):
    out = subprocess.run(["ffprobe", "-v", "error", "-show_entries",
        "format=duration", "-of", "json", ruta], capture_output=True, text=True)
    return float(json.loads(out.stdout)["format"]["duration"])

def escribir_manifiesto(id, ruta, meta):
    m = {"id": id, "archivo": ruta, "duracion_s": verificar(ruta),
         "titulo": meta["titulo"], "descripcion": meta["descripcion"],
         "hashtags": meta["hashtags"], "plataformas": meta["plataformas"],
         "publicar_en": meta["hora"], "estado": "listo"}
    json.dump(m, open(f"/media/videos/listo/{id}.json", "w"), indent=2)

Carpetas del dispositivo

/media/videos/
├── inbox/        # descargas recién terminadas
├── listo/        # vídeo + manifiesto, a la espera de revisión
├── aprobado/     # revisado por una persona
├── publicado/    # ya subido, con el ID externo
└── fallido/      # con el motivo del error

Si el agente de subida corre en otro dispositivo, se sincroniza esa carpeta con una herramienta como Syncthing o rclone, o con un bucket de almacenamiento. Lo importante es que el vídeo y su manifiesto lleguen juntos.

6. Publicación

  1. El agente de distribución vigila aprobado/Lee los manifiestos nuevos, o los recibe del Orchestrator.
  2. Comprueba antes de subirDuración, formato vertical, tamaño y que no exista ya una publicación con ese id.
  3. Sube por cuenta y plataformaElige el token de la cuenta correspondiente y llama a la herramienta del MCP de redes.
  4. Guarda el resultadoMueve el archivo a publicado/ con el ID externo y la URL.
  5. Recupera métricasVistas, retención y comentarios pasan al historial para la siguiente decisión creativa.
RedCómo se publicaA tener en cuenta
InstagramAPI de publicación de Meta, con cuenta profesionalPide una app configurada y puede requerir una URL accesible del vídeo
TikTokAPI de publicación de contenidoLa app suele necesitar revisión para publicar en abierto
YouTubeYouTube Data API, subida de vídeoTiene cuota diaria y puede limitar la visibilidad hasta verificar el proyecto

Aprobación humana primero: en el MVP, solo se mueve un vídeo a aprobado/ cuando una persona lo ha visto. Es la defensa contra publicaciones defectuosas. Etiqueta el contenido como generado con IA cuando la plataforma lo exija.

7. Estados, reintentos y errores

EstadoQuién lo poneSi falla
pendienteOrchestratorReencolar
generandoGeneraciónReintentar con límite y avisar al agotarlo
descargadoGeneraciónVolver a descargar; si el enlace caducó, relanzar el trabajo
listoPostprocesoA fallido/ con el motivo
aprobadoPersonaRechazar y pedir regeneración
publicadoDistribuciónReintentar sin duplicar (se comprueba el id)
medidoDistribuciónReintentar más tarde

Dos reglas evitan casi todos los problemas: cada paso es idempotente (repetirlo no duplica nada) y el estado vive en la base de datos, no en la memoria del agente.

8. Puesta en marcha

  1. Prueba cada pieza por separadoUn vídeo generado a mano, una descarga, una publicación en una cuenta de prueba.
  2. Configura modelos y clavesmodelos.yaml, .env y los servidores MCP, uno por uno.
  3. Conecta la cadena con aprobación humanaIdea, vídeo, carpeta listo/, revisión, publicación.
  4. Mide el coste real por vídeoCon los créditos y las llamadas de modelo de una tanda corta.
  5. Automatiza por lotesSolo cuando el flujo manual sea estable.
